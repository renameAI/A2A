# RankGPT listwise 재랭킹 — 가설·과정·결과 (실측 기록)

논문: Sun et al., *Is ChatGPT Good at Search? Investigating Large Language Models
as Re-Ranking Agents* (arXiv:2304.09542)
관련: HyDE — *Precise Zero-Shot Dense Retrieval without Relevance Labels* (arXiv:2212.10496)

구현: `app/engine/scorer_client.py` (`api_rank_listwise`, `_parse_permutation`),
`app/engine/retrieve.py` (E9 부재 폴백 경로) · 회귀 테스트 8건

---

## 1. 문제 (이전 상태)

E9(1.2B 학습 스코어러)가 죽은 GPU 서버에 갇혀 랭킹이 **bigram 겹침 휴리스틱**으로
후퇴했다. 이 엔진의 핵심 원리인 **"유사도 ≠ 보완성"이 무너진다**.

공감만세(GovTech 고향사랑기부·지역화폐 결제/정산 플랫폼) 실측:

```
후보 1. AdForUs        (광고 대행)     retr=0.1040
     2. LG CNS         (SI)           retr=0.1038
     3. 모델솔루션      (시제품)        retr=0.1038
     4. Danal           (결제)         retr=0.0997
     5. JB Financial    (지방 금융지주)  retr=0.0958
```

두 가지가 동시에 잘못됐다.

1. **후보가 키워드 매칭** — 광고사·SI가 상위. 공감만세가 파는 쪽인데 나온 건
   보완 관계가 아니라 "결제·데이터·플랫폼" 단어가 겹친 회사들.
2. **점수가 뭉갬** — 0.1040 / 0.1038 / 0.1038 / 0.0997. 변별이 사실상 없다.

1차 처방으로 API(K-EXAONE-236B) **pointwise** 폴백을 넣었으나, 후보마다 개별
호출이라 `후보 N × ~1.5s` 이고 절대점수는 여전히 뭉갤 위험이 남았다.

## 2. 가설 (논문 근거)

RankGPT의 주장 — **pointwise 절대점수보다 listwise 순열 생성이 낫다.**
후보를 한 번에 놓고 상대 비교시키면 (a) 호출이 1회로 줄고 (b) 절대 척도를 만들
필요가 없어 변별력이 산다.

여기에 우리 파이프라인의 구조적 이점을 결합한다 — **쿼리를 "우리 회사"가 아니라
`synth`(이상적 상대의 상)로 준다.** synth는 이미 보완성으로 변환된 문장이므로

> synth와의 **유사도** = 우리에 대한 **보완성**

이 성립한다. 범용 리랭커/LLM이 유사도만 잘해도 보완성 매칭이 되는 이유이고,
HyDE(가상 문서를 만들어 그걸로 검색)와 같은 구조다. 즉 **보완성 변환은 synth가
이미 수행**하고 있었다.

가설 정리:
- H1 (속도) 호출 N회 → 1회
- H2 (변별) 상대 비교라 뭉갠 점수 문제를 우회, 휴리스틱 순서를 실제로 뒤집는다
- H3 (안전) 파싱 실패·항목 누락 시에도 후보를 잃지 않는다

## 3. 과정에서 잡은 것

**LLM 출력은 깨진다는 전제로 후처리를 설계했다.** 모델은 항목을 빠뜨리거나
중복·범위밖 식별자를 뱉는다(RankGPT 논문도 후처리를 전제). 정직 규칙:

- 중복·범위밖 → 버림
- **누락된 후보 → 원래 순서로 뒤에 붙여 전수 보존** (조용한 후보 삭제 금지)
- 순열을 하나도 못 읽으면 → `None` → 휴리스틱 순서 유지 (정직 폴백)

또 하나 — **순열은 순서만 준다. 점수가 아니다.** 랭크를 0~10 점수칸에 넣으면
UI가 존재하지 않는 신뢰도를 표시하게 되므로 `learned_relatedness` /
`api_relatedness`를 비운다.

부수적으로, 검증 중 **재랭킹 경로가 통째로 무검증**이었음을 발견했다. `retrieve()`는
함수 안에서 `scorer_client`를 import해 호출 시점에 `SC`를 다시 읽는데, 기존 테스트는
`SC.score_batch`(retrieve가 쓰지 않는 함수)를 패치하고 있었다. 세션 내내 실패하던
1건의 진짜 원인이 이것이었다.

## 4. 결과 (실측)

### H1 속도 — 성립

```
listwise 순열 적용 — 1회 호출 662ms (pointwise였다면 5회)
```

후보 5개 기준 **662ms vs ~7.5s(5×1.5s) = 약 11배**.

### H2 변별 — 성립 (순서를 실제로 뒤집음)

```
휴리스틱 순서                    listwise 재랭킹 후
1. Danal        0.1124      →   1. NICE정보통신   (휴리스틱 5위)
2. Wise birds   0.1059      →   2. Danal
3. KINX         0.1056      →   3. Wise birds
4. HanmiGlobal  0.1021      →   4. KINX
5. NICE정보통신  0.1000      →   5. HanmiGlobal
```

휴리스틱 최하위(NICE정보통신, 결제·정산 인프라)를 1위로 끌어올렸다. 도메인상
결제/정산 인프라가 공감만세와 가장 가까운 축이므로 방향은 타당하다.

### H3 안전 — 성립 (후보 소실 0)

깨진 출력 10종 전수 검증, 회귀 테스트 8건 편입:

| 입력 | 결과 | 전수 보존 |
|---|---|---|
| `[2] > [1] > [3]` | `[1,0,2]` | ✓ |
| `[3] > [1]` (누락) | `[2,0,1]` | ✓ |
| `[1] > [1] > [2] > [3]` (중복) | `[0,1,2]` | ✓ |
| `[9] > [2] > [1] > [3]` (범위밖) | `[1,0,2]` | ✓ |
| 설명 섞임 / 코드펜스 / 공백없음 | 정상 파싱 | ✓ |
| 대괄호 없음 / 거절 / 빈응답 | `None`(폴백) | ✓ |

전체 테스트 **323 passed**.

## 5. 결론과 남은 한계 (정직 기록)

**랭킹 알고리즘 층은 해결됐다.** 11배 빠르고, 순서를 실제로 개선하며, 실패해도
후보를 잃지 않는다.

**그러나 이 케이스의 진짜 병목은 랭킹이 아니라 풀 구성이다.** synth가 그린 이상적
상대는 "지자체·지방 공공기관"인데:

```
전체 풀 1,140개 → 지자체·공공기관 0개
(정규식 26건 매치는 전부 오탐 — "시공사"가 "공사$"에 걸림)
```

풀은 코스닥 상장사(kq 201) + E11 코퍼스(932) = **전부 민간기업**이다. 공감만세는
B2G인데 풀에 지자체가 없으니 **어떤 랭킹 알고리즘도 이걸 고칠 수 없다.**
`weak_fallback=True`가 이 상황을 정직하게 표시하고 있었다.

→ 다음 개선은 랭킹이 아니라 **풀 밖 후보 충원**(웹 스카우트) 또는 **공공기관 풀
추가**여야 한다.

## 6. 후속 아이디어 (미착수)

RankGPT 초록의 또 다른 결과 — *"permutation distillation으로 440M 모델이 3B
supervised를 능가"*. 우리 E9는 pointwise 회귀(0~10)로 증류했는데, **순열 증류**가
랭킹 학습에는 더 낫다는 실측이다. E12 설계 시 검토 대상.
