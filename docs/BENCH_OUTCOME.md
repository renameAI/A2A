# B4·B5 — 결과 학습 루프와 실전 스니펫 증강

## B4: 결과 학습 루프

추천이 "많이 찾힌 검색어"가 아니라 **"실제로 통한 검색어"**를 올리도록,
사용자 행동을 키워드 원장에 연결한다.

### 방법론 근거

[Hu-Koren-Volinsky 2008](http://yifanhu.net/PUB/cf.pdf) (암묵 피드백 CF의 기초):
- 암묵 신호는 선호가 아니라 **신뢰도**다 (c = 1 + αr). 우리는 이를 이산
  계층으로 옮겼다: 발견(수확 1) < 저장(+2) < 초안(+4) < 답장(+8).
- **미관측 ≠ 부정.** 발견만 되고 저장 안 된 회사는 그 검색어의 실패 증거가
  아니고, "답장 없음"은 감점하지 않는다 — 지연 피드백(아직 안 온 것)과
  부정을 구분할 수 없다.
- 답장(+8)이 저장+초안(+6)보다 큰 이유: 유일한 **시장의 확인**이다. 저장·초안은
  사용자의 믿음이고, 답장은 상대의 행동이다.

### 배선

- `POST /lead-requests/{rid}/candidates/{cid}/outcome` — 저장·답장은 명시 이벤트
- 초안은 compose 성공 시 서버가 자동 기록 (사용자 신고보다 정확)
- outcome 문서가 (segment, found_by)를 보존 — 이 연결이 없으면 '통한
  검색어'를 알 수 없다
- `recommend()`: score = sim × (수확 + Σ결과가중), why에 "답장 N건" 표기

### 벤치마크 (tests/test_outcome_loop.py — 결정적, CI 게이트)

7개 속성: 콜드스타트 동률(점수를 지어내지 않음) / 답장이 동률을 깬다 /
계층 단조성 / 답장 없음 비감점 / 자기 참조 제외 / **답장 1건(수확 1) >
무결과(수확 3)** / why에 근거 표기. 전부 통과.

라이브 재현(실 store): 수확 1+답장 1건 = 0.98 > 수확 2 무결과 = 0.21.

## B5: 실전 스니펫 캡처 → 골든셋 증강

손제작 골든셋의 한계(B1~B3 공통 명시)였던 실전 노이즈를 메우는 파이프라인.

- `/search`가 히트·추출 결과·온톨로지 신호를 `dataset/snippet_log.jsonl`에
  적재 (실측: PDF 링크·깨진 문자 등 실전 노이즈 그대로 담김)
- `scripts/augment_golden_from_log.py [--emit]` — 추출 성공 히트를 골든 케이스
  스켈레톤으로 변환해 `signal_golden_staging.json`에 쌓는다
- **라벨은 사람이 확정한다.** 모델 출력을 골드로 쓰면 그 모델의 오류가 정답이
  되는 순환 논증이라, 모델 출력은 `model_said` 참고 필드로만 붙는다. 확정 후
  signal_golden.json으로 옮기고 model_said는 삭제.

첫 수확(실검색 1회): 로그 59건 → 스테이징 후보 8건 (전부 negative 후보 —
기업 목록 페이지 스니펫엔 사건이 드물다는 실전 분포 자체가 발견이다).

## 남은 한계

- 답장 기록은 사용자 자진 신고다 — 메일 발송을 우리가 안 하므로(send_blocked
  설계) 자동 검증 불가. 신고 유인은 UI 스탬프("다음 검색 추천에 반영")로만.
- 가중치(2/4/8)는 HKV의 구조를 따랐지만 값 자체는 캘리브레이션 안 됨 —
  결과 데이터가 수십 건 쌓이면 답장 예측력으로 재조정할 것.
- 한국어 쿼리 ↔ 원장(일본어) 토큰 불일치로 유사도 문턱에 걸리는 경우 실측 —
  온톨로지 축 토큰(한국어)이 비교면일 때는 완화되나, 첫 검색 전(쿼리만 있을
  때)의 교차언어 매칭은 열린 문제.
